# Adding an on-board shell test

MUS on-board tests use one controller-side pytest wrapper and one standalone
POSIX shell script. The common runner handles SCP, SSH, result parsing, Allure,
failure preservation, and script cleanup.

## Create the two test files

Copy these templates into a new feature directory:

```text
functional_tests/templates/on_board_test_template.sh
functional_tests/templates/test_on_board_template.py
```

The resulting feature should look like:

```text
functional_tests/<feature>/
├── on_board_scripts/test_<feature>.sh
└── test_<feature>.py
```

Keep case titles, purposes, and expected results in the pytest file. Do not add
a separate case YAML. The shell script must remain standalone so an RD can copy
it directly to a minimal OpenWrt or Buildroot DUT.

Every selected pytest case executes directly. Tests that change services,
interfaces, or firmware state must implement snapshot, restore, and restore
verification inside their standalone shell script.

## Shell contract

The script must accept `-t <case-id>`, `-l`, and
`--restore-mode always|on-success|never`. Its lifecycle is:

```text
precondition -> snapshot -> test actions -> assertions -> restore -> verify
```

It must emit exactly one final machine-readable line:

```text
MUS_RESULT_V1|case=<id>|test=<PASS|FAIL|SKIP|ERROR>|restore=<PASS|FAIL|PRESERVED|NOT_REQUIRED>|passed=<n>|failed=<n>|skipped=<n>
```

Exit codes are part of the contract:

| Code | Meaning |
| ---: | --- |
| 0 | Test passed and the requested restore policy completed |
| 1 | Test failed; restore either passed or was intentionally preserved |
| 2 | DUT-side setup or precondition error |
| 3 | Restore or restore verification failed |
| 4 | Invalid script arguments or unknown case |
| 77 | Case is not applicable and was skipped |
| 255 | SSH transport failure, generated by the controller |

Never report a missing prerequisite as PASS. Use `skip` only when a test is
legitimately not applicable; use exit 2 when the intended DUT environment is
broken.

## Restore rules

- Normal RD execution defaults to `on-success`: successful cases restore the
  snapshot; a failed case stops pytest and preserves the DUT for debugging.
- `--continue-on-failure` selects `always`: every case restores and verifies
  its snapshot before the next case starts.
- `--restore-mode never` is an explicit debugging mode and cannot be combined
  with `--continue-on-failure`.
- Restore or contract failures stop the entire run, including CI, because the
  DUT baseline can no longer be trusted.

Snapshot every value the test can change. Restore actions alone are not enough;
`verify_restored_state` must read the DUT again and compare it with the snapshot.

## Validate a new script

Before using hardware:

```bash
/bin/sh -n functional_tests/<feature>/on_board_scripts/test_<feature>.sh
make test TYPE=functional_tests ENV=dut115 \
  TESTCASE=<feature>/test_<feature>.py \
  OPTS="--collect-only"
```

Then select and run one case first. Review the raw DUT log, parsed MUS result,
and restore status in Allure before enabling CI continuation.
